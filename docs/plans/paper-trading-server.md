# ペーパートレード用サーバー(Worker + DB を AWS へ)

状態: **承認済み(2026-10-05、推奨案)**。東京リージョン(ap-northeast-1)、CloudFormation で定義する。構築は Unit 0(利用者による AWS の準備)が終わってから始める。

決定の経緯: 2026-10-05、利用者が「戦略検証のためにペーパートレードを止めずに続けるサーバーを用意する」と決めた(B案: EC2 + RDS + Secrets Manager、公開ポートなし、月額の目安 $30〜45)。この計画書はその実行手順を定める。

## 1. 目的

ペーパートレード([paper-trading-live-data.md](paper-trading-live-data.md))の効果測定は、トレーディング Worker が止まらないことが前提になる。手元 PC では Worker が約2日止まり、各ボットで12本の4h足が評価されなかった(2026-10-05、`report_paper_performance.py` のデータの健全性で確認)。

必要な検証期間は、仕組みの確認に1〜2か月、想定範囲との比較に6か月〜1年。その間、PC の電源・スリープ・再起動に左右されずに Worker を動かし続ける。

これは**戦略検証のための環境**であり、製品の公開ではない。

## 2. 対象と対象外

| 対象 | 対象外 |
|---|---|
| トレーディング Worker(`python -m app.trading.worker`) | 画面(フロントエンド)・公開 API |
| PostgreSQL(ボット・元帳・約定・ローソク足) | OIDC・RBAC の本番設定、ライセンス(Horizon 5 B/C) |
| 手元 DB の記録の引き継ぎ | 市場データ Worker・リアルタイム配信 |
| 止まったときの通知 | 本番取引(別プロジェクト扱い。既存の制限は緩めない) |

画面での確認や `report_paper_performance.py` などの集計は、これまでどおり手元 PC から行う(後述の「手元からの接続」)。

## 3. 前提(コードから確認した事実)

- Worker に必要な設定は `DATABASE_URL` だけ。取引所の秘密情報は使わない。
- Worker は毎回の評価の前に、Binance の公開 API(キー不要の klines)から価格を更新する。外向きの HTTPS(443)だけあればよい。
- ボット起動時の確認(`bot_lifecycle.validate_bot_startup`)は、DB 上の接続設定に `secret_ref` があり状態が verified であることだけを見る。この行は pg_dump で一緒に移る。
- 戦略の判定には直近260本の足が必要。ローソク足も含めて DB ごと移す。
- 手元 DB の大きさ(2026-10-05 時点): **全体 1,054 MB**。ほぼすべてが `candle`(1,040 MB、約267万行)で、その他は合わせて数 MB。PostgreSQL 18.6。
- Python は 3.13(`pyproject.toml`)。スキーマは Alembic で管理している。
- 手元 PC のつなぎ(タスクスケジューラでのログオン時自動起動)は PR #103 で用意済み(`scripts/windows/`)。

## 4. 構成

```text
[手元PC] --(SSM ポートフォワード)--> [EC2: trading worker (systemd)] --(5432, VPC内)--> [RDS PostgreSQL]
                                          |                                                 ^
                                          +--(HTTPS 443, NAT なし: パブリックサブネット) --> Binance 公開API
                                          +--> Secrets Manager (DB 接続情報)
                                          +--> CloudWatch (ログ・死活の監視) --> SNS --> メール
```

| 部品 | 内容 | 月額の目安(東京) |
|---|---|---|
| EC2 | t4g.small(ARM、2 vCPU / 2 GB)。Amazon Linux 2023。公開 IP あり、**受信ルールなし** | 約 $15 |
| RDS | db.t4g.micro、PostgreSQL、gp3 20 GB、シングル AZ、自動バックアップ7日 | 約 $15〜18 |
| Secrets Manager | DB 接続情報 1件 | 約 $0.4 |
| CloudWatch / SNS | ログ、死活アラーム、メール通知 | 約 $1〜3 |
| 公開 IPv4 | EC2 の 1件 | 約 $3.6 |
| 合計 | | **約 $35〜40** |

判断の理由:

- **NAT ゲートウェイを使わない**: NAT は月 $40 以上かかり、予算を超える。EC2 をパブリックサブネットに置き、受信ルールを持たないセキュリティグループで守る。外向きの通信だけを許す。
- **RDS はプライベート**: 公開アクセスは無効。EC2 のセキュリティグループからの 5432 だけを受ける。
- **操作は SSM のみ**: SSH の鍵もポート 22 も使わない。手元からの DB 接続は SSM のポートフォワードで行う。
- **シングル AZ**: 検証用なので、可用性より費用を優先する。障害時は自動バックアップから戻す(数時間の停止は「評価されなかった足」として記録に残り、後から分かる)。
- **ARM(t4g)**: 依存ライブラリが ARM 版を提供していることを Unit 3 で確認する。だめなら t3.small(約 $20)に替える。

## 5. 実装の単位

各 Unit は、前の Unit が終わってから着手する。AWS の認証情報が必要な操作は利用者が行い、Agent は手順書・スクリプト・設定ファイルを用意する。

### Unit 0: 利用者が行う準備

- AWS アカウント、請求アラート(例: 月 $50 で通知)、作業用 IAM ユーザーまたは SSO。
- リージョンの決定(推奨: 東京 ap-northeast-1)。
- 通知を受けるメールアドレス。

完了条件: 利用者が「準備できた」と伝える。

### Unit 1: インフラの定義

- VPC(パブリックサブネット1つ + RDS 用のプライベートサブネット2つ)、セキュリティグループ、EC2 の IAM ロール(SSM・Secrets Manager の読み取り・CloudWatch Logs)、RDS、Secrets Manager、SNS。
- 定義はコードで残す(推奨: CloudFormation のテンプレート1つ。追加のツールを入れずに AWS CLI だけで適用できるため)。置き場所は `infra/aws/paper-trading/`。
- RDS の PostgreSQL のバージョンは、手元(18)と同じメジャーを選ぶ。RDS が 18 を提供していない場合は、提供されている最新版にして、Unit 2 の復元で互換性を確かめる。

検証: `aws cloudformation validate-template`、適用後に EC2 から SSM で接続できること、EC2 から RDS の 5432 に届くこと、外から EC2 にどのポートも開いていないこと。

### Unit 2: データの引き継ぎ(リハーサル)

- 手元で `pg_dump -Fc`(約 1 GB。圧縮で小さくなる)、S3 経由または SSM ポートフォワード経由で RDS に `pg_restore`。
- 復元後に Alembic のリビジョンが手元と一致すること、主要テーブルの行数が一致することを確かめる。
- この時点ではサーバーの Worker は**動かさない**(手元の Worker が引き続き動いている)。リハーサルの DB は Unit 4 で作り直す。

検証: 行数の比較スクリプト(読み取りのみ)、手元からポートフォワードで `report_paper_performance.py` を RDS に向けて実行し、手元と同じ結果になること。

### Unit 3: Worker の配置

- EC2 に Python 3.13 とアプリを配置する。リポジトリの main から特定のコミットを取得し、依存ライブラリを入れる。
- 起動用のスクリプト: Secrets Manager から接続情報を読み、`DATABASE_URL` を組み立てて `python -m app.trading.worker` を起動する。秘密情報はディスクに書かない。
- systemd のサービス(`Restart=always`、OS 起動時に自動起動)。ログは journald → CloudWatch Logs。
- 更新手順(新しいコミットへの入れ替え)も手順書に書く。

検証: リハーサル DB に対して、**ボットを動かさない状態**で起動・停止・再起動・OS 再起動後の自動起動を確かめる(稼働中のボットがある DB で2つの Worker を同時に動かさないため。下の「リスク」参照)。

### Unit 4: 切り替え

二重稼働を避けるため、次の順で行う。足の確定は4時間ごと(UTC 0/4/8/12/16/20時)なので、**足の確定の直後**に始め、次の確定までに終える。

1. 手元の Worker を止め、タスクスケジューラの自動起動を無効にする(PR #103 の登録を解除)。
2. 手元で最終の `pg_dump`、RDS を作り直して `pg_restore`、行数を比較。
3. サーバーの Worker を起動。
4. 次の足の確定後に、12ボットすべてが評価されたことを確かめる(`check_paper_parity.py`、`report_paper_performance.py` のデータの健全性)。
5. 手元 DB はそのまま残す(戻すための控え)。手元の Worker は再び有効にしない。

戻す手順: サーバーの Worker を止める → RDS から `pg_dump` → 手元に復元 → 手元の自動起動を戻す。

### Unit 5: 監視と通知

- 死活: Worker のプロセスが止まったら、または一定時間ログが出なかったら、CloudWatch アラーム → SNS → メール。
- 評価の漏れ: 4h 足の確定後に評価されていないボットがあれば通知する。既存の `find_unevaluated_bars` を使う小さな確認を、EC2 の systemd タイマーで1時間ごとに動かし、結果をログに出してメトリクスフィルターで拾う。
- 請求: Unit 0 の請求アラート。

検証: Worker を手で止めて通知が届くこと、戻したら解除されること。

### Unit 6: 運用の手順書

`docs/knowledge/` に、日々の確認(月1回のレポート)、アプリの更新、止まったときの対応、バックアップからの復元、費用の確認、片付け(検証が終わったときの削除手順)をまとめる。

## 6. テストと検証の方針

- アプリのコードの変更は最小にする(起動スクリプトと監視用の確認だけを想定)。追加するコードには、これまでどおりユニットテストと ruff / mypy / pytest を通す。
- インフラはテンプレートの検証と、各 Unit の「検証」に書いた実地の確認で担保する。実行できなかった確認は、未実行として報告する。

## 7. リスク

| リスク | 影響 | 対策 |
|---|---|---|
| 切り替え中に手元とサーバーの Worker が同時に動く | 同じ足で二重に注文し、元帳が壊れる | Unit 4 の順序(手元を止めて自動起動を無効にしてからダンプ)。Unit 3 の確認はボットのない状態で行う |
| 引き継ぎの漏れ・不一致 | 記録の欠落、ボットの状態の不整合 | 行数の比較、レポートの一致の確認。手元 DB を控えとして残す |
| 想定外の費用 | 予算超過 | NAT を使わない、請求アラート、月1回の費用確認 |
| サーバーの停止(AZ 障害、更新ミス) | 足の評価漏れ | systemd の自動再起動、死活通知、評価漏れの通知。漏れはレポートに残る |
| 秘密情報の漏えい | DB への不正アクセス | 公開ポートなし、RDS は非公開、接続情報は Secrets Manager のみ、IAM ロールは最小権限 |
| ARM で依存ライブラリが動かない | 構築の遅れ | Unit 3 で確認し、だめなら x86(t3.small)へ |

## 8. 利用者の決定(2026-10-05)

1. この構成と費用(月 約 $35〜40)で進める。
2. リージョンは東京(ap-northeast-1)。
3. インフラは CloudFormation で定義する。
4. 通知先のメールアドレスは、Unit 0 で利用者が SNS に登録する(リポジトリには書かない)。

Unit 0 の準備ができた時点で Unit 1 から始める。それまでは手元 PC の自動起動でつなぐ。

## 9. 他の構成との費用比較と損益分岐点(2026-10-12、再確認)

2026-10-12、アプリ全体を AWS に置く場合と比べたうえで、利用者がこの計画の構成(その日の会話では「A案」と呼んだ。冒頭の「決定の経緯」にある「B案」は 2026-10-05 の別の比較での呼び名で、同じ構成を指す)で進めることを再確認した。

単価は東京リージョンのオンデマンドの概算(2026-10-12 時点で AWS の最新価格とは照合していない)。**Unit 0 で AWS Pricing Calculator を使って確かめ直す。** 円は 1ドル≒150円で換算。

| 構成 | 中身 | 月額の目安 |
|---|---|---|
| **この計画(Worker + DB)** | §4 のとおり。EC2 t4g.small + RDS db.t4g.micro、NAT・ALB なし | **約 $35〜40(約6,000円)** |
| アプリ全体・最小 | API・画面・3つの Worker を EC2 t4g.medium 1台に同居、HTTPS は EC2 上で終端、RDS はシングル AZ。ドメイン・Route 53 が加わる | 約 $50〜70 |
| 冗長構成 | ALB + ECS Fargate(API 1 + Worker 3)+ NAT Gateway + RDS マルチ AZ + WAF | 約 $200〜250 |

費用を押し上げるのは NAT Gateway(月 $45〜)・ALB(月 $20〜)・RDS のマルチ AZ(約2倍)。この計画はどれも使わない。画面を外から見る必要が出たら、まず「アプリ全体・最小」へ広げる(冗長構成は検証用途には過剰)。

### 損益分岐点(本番取引に進む場合の目安)

年間の固定費 ÷ 年率 = 固定費を回収できる元本。年率は [01-system-overview.md](../overview/01-system-overview.md) §7 の検証結果(6銘柄分散、手数料・スリッページ込み)。

| 構成 | 年間の固定費 | 年率 +6.4%(検証全期間) | 年率 +3%(控えめ) | 年率 +0.4%(2025〜2026年) |
|---|---|---|---|---|
| この計画 | 約7.2万円 | 約110万円 | 約240万円 | 約1,800万円 |
| アプリ全体・最小 | 約11.7万円 | 約180万円 | 約390万円 | 約2,900万円 |
| 冗長構成 | 約40.5万円 | 約630万円 | 約1,350万円 | 約1億円 |

- サーバー代以外(取引所の実手数料と想定の差、税、その他のサービス)は含めていない。
- 同じ量の買い持ちは年率 +7.2% だった。この戦略の価値は利回りではなく最大 DD の小ささ(5.8% 対 13.6%)にあるので、本番に進むかどうかは利回りだけでなくその差で判断する。
- 数字はペーパートレードで検証結果に近い利回りが出ることが前提で、まだ確かめられていない。本番取引そのものは別プロジェクト扱いのまま。
