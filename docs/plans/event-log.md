# イベントログ(検索できる API と画面)

状態: 実装済み(2026-10-08)。FR-UI-09。フロントエンドの視認性向上・仕様対応の第4弾。

## なぜ

通知は「そのときの知らせ」で、確認済みにすると見えにくくなる。システム状態は「いま」の姿だけを出す。取引停止・Worker の停止・Bot の失敗・台帳の不整合・
届かなかった通知が、いつ・なぜ起きたかを、あとから追う場所が無かった(`system_event` には残っているが、読む API も画面も無かった)。

## 追加したもの

- **API**(読み取りのみ、ワークスペースのメンバーなら誰でも):
  - `GET /workspaces/{id}/events`: 新しい順。絞り込みは、重要度(複数)・カテゴリ・種別・原因コード・Bot・相関ID・期間(`from_time` / `to_time`)・メッセージ内の語(`q`)。
    1ページ50件(最大200)。ページ送りは `before` + `before_id`(`occurred_at` と `id` の keyset)。同じ時刻のイベントが並んでも、取りこぼしも重複も出ない。
  - `GET /workspaces/{id}/events/facets`: そのワークスペースに実在する重要度・カテゴリ・種別・原因コード(絞り込みの選択肢)。
  - `app/monitoring/event_log.py`、`app/api/routes/events.py`、`app/schemas/events.py`。新しい表やマイグレーションは無い(`ix_system_event_workspace_time` を使う)。
- **画面**(`/workspaces/{id}/events`、ナビに「イベントログ」): 期間・カテゴリ・原因・種別・Bot・語・重要度の絞り込み、新しい順の一覧(重要度・カテゴリ・時刻・メッセージ・原因・対象Bot)、
  「詳細」でイベント種別・発生元・相関ID・payload、「同じ一連のイベントだけ表示」で相関IDを指定して、その経緯だけを表示、「さらに古いイベントを読み込む」、「条件をクリア」。
  原因とカテゴリは日本語で出す(原因は取引停止の画面と同じ言葉)。取得に失敗したときは、空の一覧ではなく、エラーを出す。

## 決めたこと

- **Bot の絞り込み**は、(a) 対象がそのBot(`target_type='bot'`)、(b) payload の `bot_id` がそのBot(連敗・ドローダウンのロックは口座単位の halt で、payload にBotを持つ)、
  (c) payload の `bot_names` にそのBotの名前がある(Worker 停止の通知は、対象Botを名前で列挙する)、のどれか。
- **相関ID**: 同じ出来事の `system_event` と outbox(と、緊急停止なら監査ログ)は同じ相関IDを持つ。画面は、相関IDで絞って一連を見せる(いまは `system_event` だけ)。
- **期間の既定は直近7日**(「すべて」も選べる)。語の検索は、`%` と `_` を普通の文字として扱う(LIKE のワイルドカードにしない)。語の入力は、少し止まってから検索する。
- 画面は自動更新しない(ログは見ている間に動かないほうがよい)。「更新」で再検索する。
- 閲覧は Viewer 以上。`payload` は識別子・件数・レベルだけで、秘密を含まない(`contains_sensitive_data=false` を DB が強制)。

## 未検証・限界

- 重要度が `error` 以外のイベント(取引停止・緊急停止・通知の失敗)は、ローカル DB に無く、ブラウザでは見ていない(PostgreSQL と単体テストのみ)。
- 相関IDで追えるのは `system_event` だけ。同じ相関IDの監査ログ(`audit_log`)や outbox の配信状況は出さない。
- 古いイベントを消す仕組みは無い(増え続ける)。件数が多くなったら、保持期間を決める。
