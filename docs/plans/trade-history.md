# 取引履歴(約定と建玉)

状態: 実装済み(2026-10-11)。FR-UI-12。取引の見える化の第1弾(第2弾: 判断の履歴=シグナルとリスク判定、第3弾: チャートへの重ね表示)。

## 方針

サーバーでの稼働を待たずに作る。注文・約定・台帳・建玉は既に記録されていて、足りなかったのは読む API と画面だけ。承認済みの戦略(4h足のDonchian)は取引が少ない
(バックテストで銘柄ごとに2.7年で40〜46回)ので、実データが溜まるのを待つと、数週間は画面を確認できない。

## 追加したもの

- **API**(読み取りのみ、ワークスペースのメンバーなら誰でも、`app/trading/application/trade_history.py`、`app/api/routes/trade_history.py`):
  - `GET /workspaces/{id}/fills`: 約定を新しい順に。絞り込みは、口座・Bot・銘柄・売買・期間。1ページ50件(最大200)、ページ送りは `before` + `before_id` の keyset(`executed_at`, `id`)。
    各約定に、注文(種類・状態・クライアント注文ID)、価格・数量・約定代金・手数料、**確定損益**(決済した約定の、手数料前の損益。台帳の `realized_pnl`)、**きっかけ**、Bot。
    合計(約定数・手数料・確定損益)を、**絞り込みに合うすべての約定**について、通貨(quote asset)ごとに返す(ページの分だけではない)。
  - `GET /workspaces/{id}/position-history`: 保有中の建玉を先に、次に決済済みを新しい順に。状態・Bot・銘柄で絞り込み、`limit` / `offset`。
    決済済みの建玉は、向き・平均建値・損切り・確定損益・建てた時刻と決済した時刻を持つ(数量は0。サイズは約定が持つ)。
- **画面**(`/workspaces/{id}/trade-history`、ナビに「取引履歴」): 「約定」と「建玉」の切り替え。
  約定は、時刻・Bot・銘柄・売買・数量・価格・約定代金・手数料・確定損益・きっかけの表と、合計(手数料の前後の損益)、各行の「詳細」(注文ID・約定ID・クライアント注文ID・注文の種類と状態)。
  建玉は、状態(保有中 / 決済済み)・Bot・銘柄・向き・数量・平均建値・損切り・確定損益・建てた時刻と決済した時刻・保有期間。
  Bot・売買・期間(既定は直近30日)で絞り込み、「さらに読み込む」で古い約定を読む。0件のときは理由を、読めないときはエラーを出す(空の表を出さない)。

## 決めたこと

- **きっかけは、注文を作った側がつける `client_order_id` の接頭辞から読む**: `dummy-`=シグナル、`stop-`=損切り、`dote-close-`=ドテンの決済、`emergency-close-`=緊急停止の決済。どれでもなければ手動。
  新しい列や表は作らない。接頭辞は `bot_evaluation` と `emergency_stop` が決めていて、読む側(`order_reason`)にテストがある。
- **約定のBotは、その口座・銘柄で動くBot**(1口座=1Bot=1銘柄)。同じ口座・銘柄に複数のBotがあれば、古いほう。Botの無い注文(手動)は「手動」と出す。
- **合計は通貨ごと**(JPY と USDT は足さない)。確定損益は手数料の前、手数料は別に出して、「手数料後」を並べる(Bot管理の損益と同じ定義)。
- 約定の「スリッページ」は出さない(約定価格に含まれ、基準の価格を保存していない)。
- 何も保存しない。台帳と建玉は、台帳照合(`ledger_reconciliation`)が整合を見ているので、画面とのずれは検知される。

## 検証

- 実 PostgreSQL(捨て DB、確認後に削除): `test_trade_history_postgres.py` 7件。**本物の `place_order`** の取引で、買いと損切りの決済が、きっかけ・Bot・確定損益(-20)・約定代金つきで出ること、
  合計がページ外の約定も含むこと(手数料 0.1% の合計)、各絞り込み、keyset のページ送りで重複・取りこぼしが無いこと、他のワークスペースの約定が見えないこと、きっかけの接頭辞、建玉(保有中が先、決済済みの確定損益 +20)。
- 単体: `test_trade_history_api.py` 11件、`TradeHistoryPanel.test.tsx` 14件、`AppShell.test.tsx`、`routes.test.ts`。
- ローカル DB・ブラウザ(実データ。BNBUSDT の、2026-10-05 の買いと、10-07 の損切り): 約定2件、合計「約定 2件 / 手数料 33.02 / 確定損益 -315.58(手数料後 -348.6)」(Bot管理の損益と一致)、
  売りだけに絞ると合計も1件分に変わる、「詳細」で注文IDが開く、建玉タブで「決済済み・保有期間 2日と12時間」。幅375pxでは、ページが横にはみ出さず、表だけが箱の中で横にスクロールする。

## 未検証・限界

- 保有中の建玉がある状態、ドテン・緊急停止の決済の行は、ローカル DB に無く、ブラウザでは見ていない(PostgreSQL の取引と単体テストでは、きっかけの判定と保有中の建玉を確認)。
- 決済済みの建玉に、数量と決済価格は無い(建玉の行が数量を0にするため)。往復の取引としてまとめるには、約定から組み立てる必要がある(次の段階)。
- 約定の履歴は、取引の少ない現状に合わせた表で、損益の推移のグラフは含めない(データが溜まってから)。
