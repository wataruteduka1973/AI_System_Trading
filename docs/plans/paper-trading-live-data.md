# 実データでのペーパートレード

## 目的

バックテストで最良だった「4h donchian_55_20 + 損切りのみ(利確なし)」を、Binance本番の公開価格
(キー不要)でペーパートレードとして動かし、未来のデータで検証する
(`docs/plans/multi-asset-diversification.md`、2026-09-30 利用者と合意)。

- 範囲: まずBTCUSDTで仕組みを完成させ、動作を確認してから残り5銘柄(ETH/XRP/ADA/LTC/BNB)を追加する。
- 初期資金: 合計1,000,000 USDT(バックテストと同じ)。6銘柄になった時点で1銘柄あたり1/6。
- 約定: 既存の完全な自前シミュレーション(`order_flow.py`)のまま。本物の注文は一切出さない。

## 承認ゲート「Binance Public履歴の併用」の範囲拡大(2026-09-30 利用者承認)

従来の承認は「検証用の履歴取得専用、発注・約定には一切使わない」。本計画は、公開価格を
ペーパートレードのシグナルの入力にも使う。発注・約定に使わない点は変わらない。

| 項目 | 内容 |
|---|---|
| Testnetとの差 | Testnetの短時間足は95〜99%が値動きゼロで検証に使えない(確認済み)。本番の公開価格は実市場の値動き。約定は引き続き自前のシミュレーションで、Testnet・本番のどちらにも注文しない。 |
| 画面表示 | 公開データの銘柄は、既存の「検証用」表示と同じく `binance_public` の別instrumentとして区別する。 |
| 利用規約 | 認証不要の公開エンドポイント(`/api/v3/klines`)を、個人の検証目的で、低頻度(4h足の確定を数分おきに確認)で取得する。 |
| source識別 | 公開価格の足は `binance_public` exchangeの別instrumentに保存され、Testnetの足とは混ざらない。 |

## 確定した仕様(2026-10-01 利用者と再確認)

ライブはバックテストで検証した形と一致させる。一致しない部分は、バックテストとの比較(Unit 4)で
差が出る原因になるため、変える場合は再検証してから変える。

| 項目 | 仕様 |
|---|---|
| 銘柄・資金 | BTC/ETH/XRP/ADA/LTC/BNB(USDT建て)。合計1,000,000 USDTを各1/6に配分し、**BTC単独の期間も最初から1/6(166,667 USDT)** で動かす。残りは他の銘柄の追加時に使う |
| 時間足 | 4h |
| 買い | 終値が直前55本の最高値を初めて上抜けた足(`donchian_breakout_signal`、55/20) |
| 売り | 終値が直前20本の最安値を初めて下抜けた足。売りは絞らない |
| 損切り | エントリー時に、Risk Gateの `stop_distance`(Binance: ATR(14)×2)だけ下に置く。次の足から安値で判定し、窓開けなら始値で約定 |
| 利確 | なし |
| 買い増し | **バックテストと同じ**: 保有中に新しいブレイクアウトが出たら、Risk Gateの上限(保有は資金の25%まで)の範囲で買い増す。損切り価格は最初のエントリーのまま |
| 空売り | しない(Binance現物、Risk Gateの `binance_no_short`) |
| 注文の大きさ | Risk Gate `conservative-v1`: 資金の0.5% ÷ 損切り幅。ただし1注文は使える現金の10%まで、保有は資金の25%まで(4hでは10%の上限で決まることが多い) |
| 新規注文の停止 | 日次損失2%、週次4%、ピークから5%(10%で強い停止)、4連敗、前回注文から15分以内、データ遅延2本以上 |
| ロックの解除 | **月次で見直して人が解除する**(バックテストの「30日ごとの解除」の前提とそろえる)。自動解除はしない |
| 報酬/リスク比 | Risk Gateの `min_reward_risk` 判定は比率が固定値2.0のため常に通り、**実質的に判定していない**。利確なしの方針と矛盾しないため、現状のまま変えない |
| 約定 | 自前のシミュレーションのみ(`order_flow.py`)。手数料は約定代金の0.1%、スリッページは0(バックテストと同じ) |

## 足りないもの(調査結果)

1. 公開価格の継続的な取り込みが無い。公開価格はスクリプトによる一括backfillだけで、ライブの価格取り込み
   (Worker・ストリーム)はTestnetのクライアントに固定されている。
2. 戦略が固定。`bot_evaluation.evaluate_bot_on_latest_bar` は `generate_dummy_signal` を直接呼び、読み込む足は
   直近30本だけ(donchian_55_20には最低57本、ATRの計算には260本が必要)。
3. ライブに損切りが無い。損切り価格を保存する場所が無く、`order_flow` の約定は常に直近の終値。
4. ~~ボットのexchange_codeの正規化が必要~~ → 不要と判明(2026-10-02)。ボット・口座は既存のBinance Testnetの
   接続を使い、Risk Gate・`order_flow` は取引所を接続から決めるので、既に `binance`(手数料0.1%、空売りなし、
   注文上限)になる。代わりに、`binance_public` の銘柄を使うボットは接続の取引所が `binance` でなければ
   起動を拒否する(ルールの合わない組み合わせを防ぐ)。

## 実装単位

### Unit 1: 公開価格の確定足を継続的に取り込む(完了 2026-10-01)

実装: `public_research.refresh_public_klines`、`app/trading/application/public_price_refresh.py`、
トレーディングWorker(`app/trading/worker/__main__.py`)の各ポーリングの前に実行。
次の足が確定しているはずのときだけ公開APIを呼ぶ(4h足なら1本につき1回)。保存済みの最新の足から
取り直すので、Workerが止まっていた間の欠けは次の取り込みで埋まる。品質は `complete`。
実API・実DBで確認: 前日の取得以降の空白8本を取り込み、未確定の足は保存せず、直後の2回目はAPIを
呼ばずに0本。

- `public_research.py` に、指定instrument・時間足の直近数本を取得して確定足だけをupsertする関数を追加する。
- 稼働中のボットのうち `binance_public` のinstrumentを使うものについて、トレーディングWorkerの各ポーリングの
  前に実行する。専用Workerは新設しない(4h足の確定を数分以内に拾えれば十分で、Workerを増やす運用コストに
  見合わない)。

### Unit 2: 戦略をボットごとに選べるようにする(仕様は2026-10-02 利用者承認)

完了(2026-10-02)。実装: `live_strategies.py`、`bot_evaluation.evaluate_bot_on_latest_bar`、
`bot_lifecycle.validate_bot_startup`。実DBの既存の戦略バージョン(`dummy_sma_crossover`)が新しい起動前チェックを
通ることを確認した。
- `StrategyVersion.definition` の `kind` でシグナル関数を選ぶ(`app/trading/application/live_strategies.py`)。
  `dummy_sma_crossover`(`period`)→ `generate_dummy_signal`(従来どおり)、`donchian_breakout`
  (`entry_period`/`exit_period`)→ `generate_donchian_breakout_signal`。研究用の一覧(`research_strategies.py`、
  スクリプトの表示名で引く)は使わない。ライブは、DBに保存され変更されない戦略バージョンの定義から決める。
- 未知の `kind`・不正なパラメータは、ボットの起動時(起動前チェック)と評価時の両方でエラーにする。
- ライブで読み込む足を `_HISTORY_WINDOW`(260本)にする(バックテストでシグナル関数に渡す本数と同じ)。
- シグナルの記録(`rationale`)に、実際に使った `kind`・パラメータ・終値を残す。
- 注文意図の利確価格(記録のみで実行はされない)は、利確を前提にする戦略(`dummy_sma_crossover`)だけに記録する。
- `binance_public` の銘柄 × Binance以外の接続は、起動時に拒否する(上記4)。
- 変えないもの: 保有中の買いシグナルはRisk Gateを通して買い増す、フラット時の売りは `binance_no_short` が拒否、
  一時停止中の動き、同じ足の二重評価の防止、反対シグナルでの決済。

### Unit 3: ライブの損切り(完了 2026-10-02、仕様は利用者承認)
- 損切りを使うかは戦略バージョンの定義の `exit_policy` で決める: `signal`(既定、反対シグナルのみ)/ `stop_loss`。
  バックテストの `stop_and_target` はライブでは拒否する(固定の利確は検証で不採用)。
- `trading_position.stop_price` を追加(migration `20261002_0010`、NULL可 = 損切りなし。既存行・手動の注文・
  `signal` の戦略は NULL)。
- `stop_loss` の戦略がフラットからエントリーしたときだけ、約定価格 − Risk Gateの `stop_distance` を保存する。
  買い増しでは変えない。
- 新しい確定足を評価するたびに、シグナルの前に判定する(バックテストと同じ順)。エントリー後に確定した足を
  すべて見て、安値が損切り価格に届いた最初の足で全量決済する。約定価格は損切り価格、窓開けなら始値
  (判定はバックテストの `_protective_exit` をそのまま使う)。決済後は同じ足のシグナル評価を続ける。
- 約定: `order_flow.PlaceOrderCommand.stop_fill_price`(ペーパーのシミュレーション専用)。保有中の
  ポジションを全量決済する成行注文にしか使えない。注文の `stop_price` と監査ログ
  `protective_exit.stop_loss` に記録する。
- 一時停止中のボットも損切りする。
- **運用ルール: 停止(stop)したボットは損切りしない**(停止中は何も評価しないため)。ボットを停止する前に、
  ポジションが無いことを確認する。ポジションを残したまま評価を止めたいときは、停止ではなく一時停止にする。
- 変えないもの: Risk Gateの既存リスクの計算(含み損による近似のまま)。損切りの損失は、連敗数・日次/週次の
  損失・ドローダウンに従来どおり計上される。

### Unit 4: BTCUSDTのペーパートレードを開始する(開始 2026-10-02 13:13 UTC、仕様は利用者承認)
- `scripts/provision_paper_bot.py --symbol BTCUSDT`(`app/trading/application/paper_provisioning.py`)で用意した。
  何度実行しても同じ結果になる(ボット名で判断し、口座・入金を二重に作らない。保存済みの戦略・リスクの
  バージョンと内容が違えば、上書きせず止まる)。
  - ワークスペース: Local Test Workspace。接続: 既存のBinance Testnet接続(起動時の認証チェックのみ)
  - ペーパー口座: USDT建て、166,667 USDT(資金の1/6)
  - 戦略: `donchian-55-20-stop-loss` v1(`donchian_breakout` 55/20、`exit_policy: stop_loss`、`paper_approved`)
  - リスク: `conservative-v1` v1(`CONSERVATIVE_V1_RULES` と同じ)
  - ボット: `btcusdt-4h-donchian`(ペーパー、4h、公開価格のBTCUSDT)
- 起動の直前に、スクリプトが公開価格を取り込む(Workerは稼働中のボットの価格しか更新しないが、起動前チェックは
  新しい価格を要求するため)。
- 判断の一致の確認: `scripts/check_paper_parity.py`(`paper_parity.py`)。記録したシグナルを同じ足で計算し直して
  比べる、稼働中に評価されなかった足(PCの停止など)を報告する、同じ期間のバックテストの取引と並べる。
  開始時点: シグナル1件一致、取りこぼし0件、取引なし。

**運用**
- トレーディングWorkerを動かし続ける(`python scripts/start_local.py` または `python -m app.trading.worker`)。
  **PCは常時起動にする**(利用者決定 2026-10-02)。エントリーはブレイクアウトが起きた足でしか発生しないので、
  その足の確定時にWorkerが止まっていると、そのエントリーは発生しない(損切りは再開時にさかのぼって判定する)。
- Workerは、Unit 1〜3を含むコードで動かす。
- 確認スクリプトを定期的に実行する(シグナルは1日6件、取引は1銘柄あたり月1回程度)。
- 連敗・DDロックは月次で見直して解除する。ボットを停止する前にポジションが無いことを確認する。

### Unit 5: 残り5銘柄を追加する(開始 2026-10-02 13:29 UTC、仕様は利用者承認)
- `scripts/provision_paper_bot.py --symbol <銘柄>` を ETH/XRP/ADA/LTC/BNB で実行した(コードの変更なし)。
  ボット `<銘柄>-4h-donchian`、各専用口座166,667 USDT。戦略 `donchian-55-20-stop-loss` v1 と
  リスク `conservative-v1` v1 は6ボットで共有(同名のものは1件ずつ)。合計の資金は1,000,002 USDT
  (166,667 × 6、端数は結果に影響しない)。
- Risk Gateの上限は口座ごとにかかり、6銘柄をまとめた上限は無い。バックテストのポートフォリオも
  「各1/6を独立に運用」なので、検証した形と一致する。
- LTCは単独では赤字だったが、検証したのは6銘柄のポートフォリオなので、予定どおり含める
  (結果を見てから銘柄を選ぶと過剰適合になる)。
- 確認: `python scripts/check_paper_parity.py --all` で6ボットをまとめて確認できる。開始時点で
  6ボットとも稼働中、価格は最新まで取り込み済み、最初の評価のシグナルがバックテストと一致(6/6)。

### Unit 6: ライブの成績をバックテストの期待値と並べて確認する

## 想定リスク

- 1銘柄あたり月1回程度しか取引しないため、数か月では統計的な優位性は確認できない(1年単位の運用が必要)。
  短期で確認できるのは、仕組みの正しさとバックテストとの一致。
- 公開APIの一時的な障害。取り込みに失敗したサイクルは評価を行わず、次のポーリングで再試行する。既存の
  データ遅延チェックが古いデータでの取引を止める。
- Risk Gateの連敗ロック・DDロックは、ライブでは人が解除する前提。バックテストは30日ごとの解除を前提に
  評価しているので、ロックがかかったら確認して解除する運用が必要。

## 新しいボットは承認済みの戦略だけで作る(2026-10-02 利用者決定)

- 研究で不採用になったSMA(`dummy_sma_crossover`)は、ライブ/ペーパーで選べる戦略から外した
  (`live_strategies.py`)。SMAで保存されたボットは起動時の確認で拒否される。既存の行は削除しない。
- Bot作成API(画面の「Bot作成」)は、承認済みの戦略(Donchian 55/20＋損切り、`conservative-v1`、4h足)で
  だけボットを作る。定義は`paper_provisioning.APPROVED_*`の1か所にあり、`scripts/provision_paper_bot.py`も
  同じ定義を使う。4h以外の時間足と、戦略バージョンの`supported_market_types`(暗号資産のみ)にない市場の
  銘柄は422で拒否する。検証していない条件でボットを動かさないため。
- SMAのシグナル生成は、研究スクリプトの比較基準(`dummy_sma5`)として残す。
- バックテストAPI(画面の「バックテスト」)も同じ承認済みの戦略バージョンを使い、ライブのボットと同じく
  `resolve_live_strategy`でシグナルと決済方針(損切り)を決める。`code_version`が`dummy-pipeline-0.1`の
  過去の実行はSMAで計算したもので、`approved-strategy-0.1`以降と比べない。
