# 複数銘柄のバックテストを1回で

状態: 実装済み(2026-10-07)。画面は未実装。2026-10-07 の利用者決定(「同期のまま、複数銘柄を1回で」)による。

## 決めたこと

- **ジョブ化しない。** バックテストは、よく使う範囲では速い(BTCUSDT 4h・2.7年が0.2秒、1hが1秒、5分足28.9万本が13秒、6銘柄の4hで2.3秒)。
  キュー・Worker・進捗画面は、通常の実行には無い問題のために足すことになる。遅くなりうるのは、足の**合計本数**だけ。
- **合計本数に上限**(`MAX_BATCH_BARS` = 300,000本。約15秒、実測の1秒あたり約2万本から)。実行の**前に**数え、超えていれば全体を断る
  (422 `batch_too_large`、銘柄ごとの本数を添える)。一部だけ実行して時間切れになるより、予測できるため。期間を短くするか銘柄を減らす。
- **1回の銘柄数は最大12**。同じ銘柄は重複できない。
- **銘柄ごとに独立した実行**。単独の `POST /backtests` と同じもの(銘柄ごとの `DatasetSnapshot`・`BacktestRun`、30日ごとのロック解除の前提も同じ)で、
  1銘柄ずつ commit する。失敗した銘柄(範囲に足が無い、など)は自分の項目に `error_code` を書いて、他の銘柄は続ける。想定外の例外は型名だけ残す。
- **ポートフォリオのシミュレーションではない。** 銘柄どうしは資金を共有しない。合算は研究用スクリプト(`scripts/research/evaluate_portfolio.py`)の役割。
- 戦略は承認済みの1つだけなので、「複数戦略」は含まない(2つ目の戦略ができるまで見送る決定のとおり)。

## API

`POST /workspaces/{id}/backtests/batch`(Operator 以上)。本文は単独の `POST /backtests` と同じ設定(`timeframe`・`from_time`・`to_time`・`initial_equity`・
`spread`・`mode`・`train_ratio`)に、`instrument_ids`(1〜12件)。

- 先に全銘柄のアクセスを確認する(404 銘柄なし、409 使えない銘柄。1つでもあれば何も実行しない)。
- 応答: `total_bars` と、リクエスト順の `items`(`instrument_id`・`symbol`・`bars`・`runs`・`error_code`・`error`)。`runs` は、`single` なら1件、`walk_forward` なら訓練と検証の2件。

## 検証

- 単体: `tests/test_backtest_batch.py`(上限の確認が実行の前であること、ちょうど上限は通ること、1銘柄の失敗が他に及ばないこと、例外のメッセージを残さないこと、銘柄数・重複・アクセス・検証・権限)。
- ローカル DB(全部 rollback、実データ): 6銘柄×4h×2024-01〜2026-09 が2.3秒で、銘柄ごとに取引40〜46件(30日ごとのロック解除の前提)。
  5分足を全期間にすると、合計957,565本で断られる。足の無い範囲は銘柄ごとに `no_candles` を返し、他の銘柄は続く。

## 既知の制限

- 画面は未実装(API のみ)。
- 上限は本数だけ。取引が多い・戦略が重いなど、1本あたりの時間が増える場合は、15秒を超えうる。
- 失敗した銘柄の前の銘柄は、すでに保存されている(全体のロールバックはしない)。
- 1分足を1年など、1銘柄で上限を超える実行は、この API では断られる。単独の `POST /backtests` には上限が無い(従来どおり)。
