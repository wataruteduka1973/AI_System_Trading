# ADR 0006: ライセンスcheck-in・顧客管理サービスを新設し、ADR 0005の「常時稼働のアクティベーションサーバーを持たない」を部分的に見直す

- 状態: 承認済み(利用者との対話により決定、詳細実装計画は別途作成)
- 日付: 2026-09-25
- 決定者: 利用者
- 記録者: Claude(このリポジトリのAIエージェント)

## 背景

Horizon5 グループC(Unit 6、`docs/plans/horizon5-implementation-plan.md`)は、Ed25519署名済み
`license.json`のオフライン検証のみでライセンス機構を実装する計画だった。ADR 0005が「常時稼働の
アクティベーションサーバーを持たない」ことを明示的に選択しているためである。

利用者とマネタイズ戦略を検討する過程で、この設計の限界が明確になった。

1. **不正利用への技術的防御力がほぼ無い。** 本ソフトウェアはPythonのセルフホスト型配布であり、
   顧客は`require_valid_license()`を含む全ソースコードに完全アクセスできる。オフライン署名検証
   だけでは、悪意を持って検証ロジック自体を除去・改変する顧客を防げない。防げるのは「期限切れに
   気づかず放置」等、善意の顧客の事故のみ。
2. **運営者に利用状況の可視性が全く無い。** 1本のライセンスが何箇所で実際に使われているか、
   運営者側からは原理的に分からない。
3. **将来のサブスクリプション化を見据えると、完全オフライン設計は相性が悪い。** サブスクリプション
   は本質的に「支払いが今も有効か」の定期的な再確認を要する。
4. **意図しない状況(ファイル紛失、想定外の期限切れ、環境移行等)でのアクセス回復手段が無い。**
   顧客が自力で復旧できず、運営者側にも顧客を特定する情報が無いため、復旧を支援する手段が無い。

## 決定内容

1. **新しい別サービス(別リポジトリ)として「ライセンス・顧客管理サービス」を新設する。**
   本リポジトリ(顧客に配布するAI_System_Trading本体)とは分離する。理由:
   - 顧客の購入者データベース・復旧トークン発行ロジックを、顧客に配布するコードへ混入させない。
   - 運営者だけが運用する管理系サービスと、顧客が自己ホストする配布物は、デプロイ先も
     責務も異なる。
2. **check-inは任意・fail-open(失敗しても起動を止めない)とする。** ADR 0005の核心的価値
   (「顧客の運用が運営者のインフラの可用性に依存しない」)は維持する。プライマリのライセンス
   検証は引き続きオフライン署名検証(Unit 6のまま)。check-inはその上に乗る付加的な可視化層。
3. **check-inで送信する情報には、購入者(契約主体)情報に加え、顧客環境内のエンドユーザー情報
   (`user_membership`/`AppUser`由来のメールアドレス・表示名・ロール・最終アクティブ日時等)
   も含める。** これは意図的なプライバシー上のトレードオフである(下記「検討した代替案」参照)。
4. **復旧トークンはセルフサービスで発行する。** 購入者が登録済みメールアドレスで本人確認し、
   自動的に新しい署名済みライセンスファイルまたは復旧トークンを受け取る。運営者の手動対応を
   要さない。
5. **本ADRはADR 0005の「常時稼働のアクティベーションサーバーを持たない」を部分的に見直す。**
   完全に撤回するのではなく、「必須の依存にはしない(fail-open)」という条件付きで、
   運営者側インフラの新設を許容する。

## 検討した代替案

### (i) オフライン検証のみを維持し、check-inを追加しない(Unit 6の当初計画のまま)

**不採用の理由**: 「不正利用を防ぐことが何よりの課題」という利用者の優先順位と両立しない。
可視性ゼロのままでは、技術的にも運用的にも不正利用に一切対応できない。

### (ii) check-inで送る情報を購入者情報のみに限定し、エンドユーザー情報は含めない

一度提示した代替案。運営者が顧客のエンドユーザーの個人情報を一切扱わずに済み、既存のOIDC設計
(運営者はエンドユーザーを一切見ない)とも矛盾しない。

**不採用の理由(利用者判断)**: 復旧トークン発行時の本人確認・行動追跡という目的も兼ねるため、
エンドユーザー情報を含めることを利用者が選択した。

### (iii) 顧客管理機能を本リポジトリ内に同居させる

**不採用の理由**: 顧客に配布するコードに、運営者専用の顧客DB・復旧ロジックが混入する。
セルフホスト配布物としての最小性・監査可能性を損なう。利用者も別サービスを推奨。

## 残存リスク(未解消)

- **プライバシー・コンプライアンス上のリスク。** エンドユーザー(顧客の従業員等、運営者と
  直接契約関係にない第三者)の個人情報(メールアドレス・表示名等)を運営者のサーバーで収集・
  保持することになる。GDPR等の適用範囲、収集の法的根拠、保持期間、削除要求への対応方針は
  **未検討**。本ADRの時点では技術設計の方向性のみを決定しており、以下は別途対応が必要:
  - 顧客向け利用規約・プライバシーポリシーへの明記(Unit 10の運用ドキュメントとの連携)
  - check-in自体を無効化できる環境変数を用意し、収集を望まない顧客が拒否できるようにする
    (収集を拒否した場合、check-in由来の復旧・可視化機能は使えなくなる旨も明記する)
  - 収集項目を実際に必要な最小限(メール・表示名・ロール・最終アクティブ日時程度)に絞る
- **復旧トークンのセルフサービス自動発行は、本人確認の強度と利便性のトレードオフを伴う。**
  メールアドレスのみでの本人確認は、購入者のメールアカウントが侵害された場合に濫用されうる。
  レート制限・監査ログ・不審なパターンの検知は詳細実装計画で具体化する。
- **署名鍵の保管場所が変わることによるリスクの変化。** Unit 6の当初想定(秘密鍵は運営者の手元、
  `scripts/issue_license.py`を都度手動実行)から、新サービスが鍵を保持してAPI経由で発行する
  形に変わる可能性が高い。この場合、鍵の露出面が「運営者のローカル環境のみ」から「常時稼働する
  サービスとそのシークレット管理」に広がる。詳細実装計画で、新サービス側の鍵管理方式
  (KMS等)を具体化すること。
- 新サービス自体の可用性・セキュリティ(認証基盤、DB、ホスティング費用)は、本ADRでは
  「別サービスとする」という方針のみを決定しており、具体的な実装・運用コストは未見積もり。

## 将来の見直し条件

- 上記「プライバシー・コンプライアンス上のリスク」について、利用規約・プライバシーポリシーの
  整備、または法務確認が完了するまでは、check-inによるエンドユーザー情報収集を本番の顧客へ
  展開しない。
- 座席数(seat)に応じた課金は本ADRのスコープ外(現時点では「1ライセンス=1インストール」の
  可視性強化に留める、利用者確認済み)。座席課金を導入する場合は、収集済みのエンドユーザー
  情報を根拠にできるが、別途利用者確認の上で再評価する。
- 詳細実装計画(データモデル、API仕様、復旧フロー、check-in送信頻度、新サービスのリポジトリ名・
  配置)は本ADRを踏まえて別途作成する。

## 影響範囲

- `docs/plans/horizon5-implementation-plan.md` Unit 6は、本ADRの決定に沿って改訂が必要
  (ライセンス発行の主経路が`scripts/issue_license.py`単体から新サービス経由へ変わる可能性、
  check-in送信ロジックの追加)。
- 本リポジトリ(AI_System_Trading)側の変更は、check-inペイロードの送信ロジック
  (`app/licensing/`配下に新設予定)と関連設定(`app/core/config.py`)に限定される想定。
  顧客DB・復旧トークン発行ロジックは新サービス側にのみ実装する。
- `docs/architecture-alignment-and-long-term-roadmap.md`のHorizon 5節を本ADRへの参照付きで
  更新する。
