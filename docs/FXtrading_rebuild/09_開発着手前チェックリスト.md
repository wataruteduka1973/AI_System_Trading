# 開発着手前チェックリスト

## 1. 現在地

現時点で以下は「基本設計の初版」として揃っている。

- 要件定義 0.4
- 現行問題とクリーン再実装方針
- 概念・論理ER図
- REST/WebSocket API基本設計
- アーキテクチャ、画面一覧、移行計画
- アルゴリズム、AI学習、リスク初期値

ただし、OpenAPI 3.1の完全なschema、PostgreSQL物理DDL、全状態遷移表、画面遷移・ワイヤーフレームは未作成である。これらは実装直前の詳細設計として作成する。

## 2. Product Gate: 事業・利用条件を確定する

- [x] 初期利用者を単一Ownerとする
- [x] 初回リリースは実市場データを使用するpaper専用とし、実注文を含めない
- [x] 同時稼働上限をworkspaceあたり5 Botとする
- [x] 通知をアプリ内＋Gmailとする
- [x] ニュース分析をMVP対象外とする
- [x] 初期は本人利用、将来は第三者へ配布・販売する
- [ ] 提供地域と想定利用形態を決める
- [x] 将来の商用利用を前提に権利・workspace分離を設計する
- [ ] 予算、MVP期限、運用時間、許容停止時間を決める

## 3. Rights Gate: 権利とクリーン実装を準備する

- [ ] 旧リポジトリとは別の空リポジトリを作る
- [ ] 旧コード、旧Git履歴、旧DB、旧HTML、旧画像をコピーしない
- [ ] 旧APIキーをOANDA、Binance、News API側で失効する
- [ ] 新しいAPIキーは開発開始時点ではpractice/test用途だけ発行する
- [ ] `LICENSE`、`NOTICE.md`、`THIRD_PARTY_LICENSES.md`、`CONTRIBUTORS.md` を用意する
- [ ] コミット時に作成者、出典、利用ライセンスを追跡するルールを決める
- [ ] 外部モデルの許可ライセンスallowlistを決める
- [ ] 公開・販売前に著作権、契約、金融規制について専門家へ確認する

推奨する初期モデルライセンス方針は、ライセンスが明示され、予定する利用方法を許可するものだけを個別承認する方式である。「無料公開」を「自由利用可能」と解釈しない。

## 4. Account Gate: 外部サービスを準備する

- [ ] OANDA practice口座を用意する
- [ ] OANDA v20 personal access tokenを新規発行する
- [ ] トークンから参照できる全sub-accountとhedging/margin/GSLO能力を記録する
- [ ] Binanceの新しい開発・検証用APIキーを発行する
- [ ] BTCJPY、MARKET、LIMIT、価格・数量filterが接続先で利用可能か確認する
- [ ] BinanceのAPIキーには出金権限を付けない
- [ ] testnetでBTCJPYを利用できない場合に備え、paper adapter＋取得済み公開市場データを検証経路とする
- [x] メール通知サービスをGmail APIに決定する
- [ ] Google Cloud project、OAuth consent、Gmail API OAuth clientを準備する
- [ ] Hugging Faceを使う場合、検索のみ匿名で行うかread-only tokenを使うか決める

秘密値は設計書、issue、チャット、ソース、`.env.example` に記載しない。

## 5. Technical Gate: 技術基盤を確定する

- [x] BackendをPython/FastAPIとする
- [x] FrontendをReact/TypeScriptとする
- [x] PostgreSQLを採用する
- [x] APIと市場データ・Bot・学習workerを分離する
- [ ] ジョブキューとWebSocket event transportを詳細設計で確定する
- [ ] Docker Composeによるlocal/dev環境を定義する
- [ ] dev、test、paper、liveを別環境として定義する
- [ ] Secret Managerを選定する
- [ ] Python、Node、PostgreSQL等のサポート版を固定する
- [ ] ADR（Architecture Decision Record）運用を開始する
- [ ] formatter、linter、型検査、テスト、依存更新方針を決める
- [ ] CIで秘密scan、SAST、依存脆弱性、ライセンスscanを有効にする

## 6. Detailed Design Gate: 実装可能な詳細へ落とす

- [ ] OpenAPI 3.1ファイルを作り、request/response/error schemaを確定する
- [x] ER図からPostgreSQL物理DDL初版を作る
- [ ] DDLレビュー後にAlembic initial migrationへ変換する
- [ ] Decimal精度、通貨、pip、tick size、step sizeの型を確定する
- [ ] Bot、注文、約定、停止、補完、モデルの状態遷移表を作る
- [ ] event typeとreason codeの正式な一覧を作る
- [ ] outbox、冪等キー、再試行、dead-letter処理を確定する
- [ ] OANDA/Binance adapterのinterfaceと契約テストを確定する
- [ ] 画面遷移図と主要画面のワイヤーフレームを承認する
- [ ] 権限マトリクスをAPI・画面操作単位で確定する
- [ ] 脅威モデルを作り、秘密漏えい、注文重複、権限昇格等を分析する

## 7. Data/AI Gate: データと学習条件を準備する

- [ ] OANDA USDJPY、Binance BTCJPYの必要履歴期間を決める
- [ ] データ利用規約、保存可否、再配布可否を確認する
- [ ] UTC、取引セッション、週末、祝日、DSTの扱いをテスト仕様にする
- [ ] 欠損・重複・異常値・補完済みデータの品質基準を決める
- [ ] 最初のbaselineアルゴリズムを1つだけ選ぶ
- [ ] AIの予測対象（方向分類、リターン、volatility等）を1つ選ぶ
- [ ] train/validation/test期間とwalk-forward方法を固定する
- [ ] 学習用CPU/GPU、メモリ、保存容量、実行時間の予算を決める
- [ ] モデル評価の最低取引回数、最大DD、baseline超過条件を決める
- [ ] 外部モデルはsafetensors、revision固定、checksum、隔離検査を必須とする

最初から多数の指標やモデルを比較せず、データパイプラインと評価の正しさを単純なbaselineで確認する。

## 8. Risk Gate: リスク値と解除権限を承認する

- [ ] `conservative-v1` の1取引0.5%、日次2%、DD5%をpaper初期値として承認する
- [ ] system hard limitをpaper向けに承認する
- [ ] live用hard limitはlive開発開始まで未確定・無効のままにする
- [ ] 停止レベルごとに許可される決済・取消操作を承認する
- [ ] 自動解除可能な原因と手動解除必須の原因を承認する
- [ ] 緊急停止を誰が実行・解除できるか決める
- [ ] gap/slippageを含むstress lossの計算条件を決める
- [ ] OANDAのmargin警戒値をpracticeデータで検証する

## 9. Test/Operations Gate: 完成条件を先に用意する

- [ ] 要件IDごとの受入テスト一覧を作る
- [ ] 金額、数量、手数料、損益、丸めの単体テストを先に作る
- [ ] 重複イベント・重複注文に対する冪等性テストを用意する
- [ ] WebSocket切断、429、timeout、部分約定、DB障害の試験を用意する
- [ ] 欠損検出・補完・再検証の試験データを用意する
- [ ] バックアップ、復元、ログ保持、監視、アラート方針を決める
- [ ] paperで24時間、その後2〜4週間の連続運転計画を作る
- [ ] 障害時の緊急停止、手動決済、APIキー失効手順を作る

## 10. 推奨着手順

1. Product/Rights Gateを承認する
2. 新しい空リポジトリとCIを作る
3. OpenAPI、物理DB、状態遷移、画面遷移を詳細化する
4. 認証、workspace、監査・イベント基盤を作る
5. OANDA/Binanceの読取専用接続と市場データを作る
6. チャート、データ品質、欠損補完を作る
7. paper口座、注文、約定、ポジション、台帳を作る
8. 単純なtechnical baselineとリスクゲートを作る
9. バックテストと長時間paper運転を行う
10. AI学習、外部モデル探索を追加する

## 11. Definition of Ready

以下を満たせば、MVP実装を開始できる。

- Product Gateの判断が文書化されている
- 旧資産と分離した空リポジトリがある
- practice/test用の接続だけが用意されている
- OpenAPI、物理DB、主要状態遷移の初版がある
- 主要画面のワイヤーフレームが承認済み
- conservative-v1とpaper用hard limitが承認済み
- 要件IDに対応する受入テストが登録済み
- 秘密、依存、ライセンスのCI検査が有効
- live取引が技術的にも設定上も無効である
