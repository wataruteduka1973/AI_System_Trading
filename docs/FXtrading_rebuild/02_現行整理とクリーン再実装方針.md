# 現行整理とクリーン再実装方針

## 1. 確認できた現行機能

| 領域 | 現行の挙動 | 新設計での扱い |
|---|---|---|
| 市場データ | Binance/OANDAクライアント、WebSocket、RESTフォールバック | 外貨FX・仮想通貨FXに対応するアダプター契約を新規定義して再実装 |
| ローソク足 | 1m/15m/1h/1dを銘柄別テーブルへ保存 | 正規化した単一テーブルへ統合 |
| チャート | OHLCVと複数テクニカル指標 | UI要件として維持。計算APIは構造化 |
| 戦略 | 指標の最適化値を使った売買判定 | 戦略版・入力・理由を保存する新エンジンへ置換 |
| ML | GNN＋Transformerによる補助判定 | MVP外。モデルレジストリ境界のみ設計 |
| リスク | データ品質、DD、ポジション、ストップ | 概念を維持し、各判定を永続化 |
| ペーパー取引 | メモリ内ウォレット＋イベント保存 | 永続台帳と決定論的シミュレーターへ置換 |
| Web API | ローソク足、ニュース、取引状態の3系統 | `/api/v1`として資源単位に再設計 |
| バックテスト | 同一AIクラスのモード切替 | ライブ処理と分離した非同期ジョブへ置換 |

## 2. 現行の主要問題

### セキュリティ・権利

- 実値らしい複数のAPI認証情報が `settings.ini` にあり、Git追跡済み。
- 設定ファイルを後からignoreしているが、履歴からは消えない。
- README、ライセンス、寄与者ごとの権利・出典記録がない。
- 生成物、DB、ログ、バイトコードが配布物に混在している。

### データ設計

- 銘柄・時間足ごとに物理テーブルが増え、拡張にスキーマ変更が必要。
- 時刻だけを主キーにするイベントがあり、同時刻の複数イベントを表現できない。
- シグナル、注文、約定、ポジション、残高の区別が曖昧。
- 金額にFloatを使用しており、金融計算の丸め誤差が発生し得る。
- ペーパー残高がメモリ中心で、状態表示時に別インスタンスが作られる。

### アプリケーション構造

- Web、データ取得、戦略、注文が同一プロセスとグローバル状態に密結合。
- 設定上のシャドーモードとコード上の強制値が二重管理。
- OANDA選択時にBinance専用設定を参照するなど、抽象化境界が成立していない。
- 履歴補完が特定取引所SDKを直接呼び、共通クライアントを迂回する。
- 再試行が再帰で実装され、停止や最大試行の管理が弱い。
- Flask開発サーバーを全インターフェースで公開し、認証がない。

### 品質・運用

- 自動テストが存在しない。
- 取引判断の根拠と使用した設定版を完全に追跡できない。
- Web APIが内部例外文を返す箇所がある。
- 画面が3秒間隔で複数APIをポーリングする。
- 学習・推論のデータリーク、モデル評価、モデル来歴の統制が不明。

## 3. クリーン再実装の原則

1. **仕様と実装を分離する。** 現行コードを読んだ結果は、機能一覧と問題報告に限定する。
2. **必要性を再承認する。** 現行にあるという理由だけで機能を採用しない。
3. **新しい語彙と境界を使う。** 新ドメインモデル、API、DB、状態遷移を本資料から新規実装する。
4. **コードをコピーしない。** 関数、クラス、SQL、HTML、コメント、テスト、定数値のコピーを禁止する。
5. **由来を記録する。** 要件、設計、コード、画像、モデル、データセットごとに作成者・日付・出典・ライセンスを記録する。
6. **独立した受入試験を先に作る。** 業務上期待する入出力からテストを作り、旧コードの出力を正解データにしない。
7. **秘密を移行しない。** 既存APIキーは失効し、新規キーを秘密管理基盤へ登録する。

## 4. 推奨する開発体制

- 仕様担当: 現行観察結果と業務要件を整理する。新実装コードを書かないことが望ましい。
- 実装担当: 承認済みの本資料と公開API仕様だけを受け取り、新規に実装する。
- レビュー担当: 旧コードとの不自然な類似、依存ライセンス、秘密混入を確認する。
- リポジトリには `NOTICE.md`、`THIRD_PARTY_LICENSES.md`、`CONTRIBUTORS.md`、設計判断記録を置く。

小規模で役割分離ができない場合も、旧コードを参照した日時と目的を記録し、実装時には旧リポジトリを開かず、本仕様だけを入力とする工程を設ける。

## 5. 機能の採否

### 維持

- OHLCVチャート
- テクニカル指標
- ペーパートレード
- データ品質・ドローダウン・ポジション制限
- WebSocketと履歴補完
- バックテスト
- 外貨FXと仮想通貨FX。ただし接続・口座・Botを独立させ、同時稼働可能にする

### 仕様を変えて維持

- 「AIトレード」は、テクニカル指標モードとAIモデルモードへ明確に分ける。
- 「売買イベント」は、シグナル、リスク判断、注文、約定へ分解する。
- 「シャドーウォレット」は、永続的な口座・台帳・ポジションへ置換する。
- 「取引所切替」は、アダプターの契約テストを満たす実装だけを追加可能にする。

### MVPから除外

- ニュースセンチメント
- アプリ内でのGNN/Transformer学習（登録済みモデルの推論は対象）
- 初期採用先以外の追加ブローカー・取引所
- 実資金注文

## 6. 既存データの扱い

- 既存SQLite DBは新製品の初期データとして自動移行しない。
- 市場データが必要なら、正規の取引所APIから新規取得する。
- 既存取引記録を参照用に残す場合は、読み取り専用アーカイブとして新DBと分離する。
- 移行が必要になった場合は、出典、取得時刻、タイムゾーン、精度を検証し、`import_batch` とチェックサムを記録する。

## 7. 完了条件

- 新リポジトリに旧コード・旧Git履歴・旧秘密情報が存在しない。
- 採用した各機能が承認済み要件IDへ結び付く。
- 主要設計判断と第三者依存関係の出典が追跡できる。
- 秘密スキャン、ライセンススキャン、類似性レビューに合格する。
